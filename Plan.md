# План тестирования и автоматизации приложения «ВХосписе»

## 1. Описание приложения и границы тестирования

«ВХосписе» — однооконное Android-приложение для сотрудников хосписа: лента новостей организации с возможностью администрирования плюс два информационных раздела.

Экраны:

1. **SplashScreenFragment** — проверка сохранённой авторизации и переход дальше.
2. **AuthFragment** — вход по логину и паролю.
3. **MainFragment** — главный экран, превью последних новостей.
4. **NewsListFragment** — полный список новостей с сортировкой и фильтром.
5. **NewsControlPanelFragment** — панель администратора: создание, редактирование и удаление новостей.
6. **CreateEditNewsFragment** — форма создания и редактирования новости.
7. **FilterNewsListFragment** — фильтр по категории, периоду и статусу.
8. **AboutFragment** — версия приложения, ссылки на политику конфиденциальности и условия использования.
9. **OurMissionFragment** — раздел «Наша миссия».
### Что не входит в границы тестирования

- **Бэкенд** Проверяется только Android-клиент: отправка запросов, обработка ответов и поведение интерфейса. Серверная логика, производительность и безопасность API вне зоны ответственности клиентского тестирования.
- **Комментарии к новостям.** В `res/layout` есть три готовых макета, но ни один класс или адаптер их не использует — функциональность не реализована, экрана не существует.
## 2. Реализованный функционал

- **Splash и авторизация.** Автоматический вход при сохранённом токене, переход на экран логина при его отсутствии или истечении.
- **Авторизация.** Вход по логину и паролю, проверка пустых полей на клиенте, разные сообщения для ошибок сети и неверных данных, выход из системы через меню.
- **Главный экран.** Превью трёх последних новостей, сворачивание блока, переход в полный список.
- **Список новостей.** Обновление жестом, сортировка по дате, фильтрация, переход в панель администратора при наличии прав.
- **Панель администратора.** Список с признаком активности, раскрытие описания, редактирование, удаление с подтверждением, добавление новости.
- **Создание и редактирование новости.** Категория, заголовок, дата и время публикации через диалоги выбора, описание, переключатель активности; проверка заполненности полей; сохранение отправляется на сервер.
- **Фильтр новостей.** Категория, период дат, статус активности (только в панели администратора).
- **О приложении и Наша миссия.** Статические информационные экраны.
## 3. Типы тестирования

| Тип | Обоснование |
|---|---|
| **Функциональное** | Основа проверки: каждый экран и сценарий должен выполнять заявленное. Без этого остальные виды тестирования не имеют смысла. |
| **UI и визуальное** | Экраны свёрстаны на `ConstraintLayout` без единого каркаса. Уже найден дефект расположения полей в `AboutFragment` — такие ошибки не ловятся компилятором. |
| **Негативное** | В коде заложены отдельные ветки обработки ошибок: пустые поля, некорректный период фильтра, отсутствие прав, отсутствие сети. Их нужно проверять намеренно. |
| **Граничных значений** | У даты публикации задана только нижняя граница, у полей заголовка и описания ограничений нет вовсе. Такие пробелы выявляются только проверкой предельных значений. |
| **Навигации** | Общее меню используется на шести экранах, переходы построены на Navigation Component. Уже найден дефект подсветки пункта меню на экране News. |
| **Работы без сети** | Все данные приходят через REST API, в коде обрабатываются `ConnectException` и `IOException`. Нужно убедиться, что интерфейс показывает сообщение, а не зависает. |
| **Устойчивость к эффекту пестицида** | Повторяющиеся тесты с одними и теми же данными со временем перестают находить дефекты. В негативных сценариях авторизации логин и пароль генерируются случайно при каждом прогоне, заголовки создаваемых новостей содержат метку времени и случайный суффикс. Использованные значения логируются, чтобы падение оставалось воспроизводимым. |

## 5. Что не автоматизируется

- **Отказ в доступе к панели администратора для обычного пользователя.** Все доступные учётные записи (`login1`, `login2`, `login3`) имеют права администратора, учётной записи без прав нет — сценарий невоспроизводим.
- **Верхняя граница даты публикации.** Требование о максимальной дате нигде не зафиксировано, сравнивать фактическое поведение не с чем. Отсутствие `maxDate` зафиксировано в чек-листе граничных значений.
- **Ограничения длины заголовка и описания новости.** Ограничений нет ни на клиенте, ни визуально; согласованных предельных значений не существует, поэтому проверка выполняется вручную.
- **Расположение полей на экране «О приложении».** Espresso проверяет наличие текста, но не взаимное перекрытие элементов. Такие дефекты ловятся скриншот-тестированием или ручным просмотром.
- **Переход по внешним ссылкам.** Открытие браузера уводит за пределы тестируемого приложения, куда у Espresso нет доступа.
- **Функциональность комментариев.** В проекте есть макеты экранов для комментариев, но кода к ним нет — экран не существует, тестировать нечего.
- **Логика бэкенда.** Серверная валидация и обработка конкурентных изменений вне границ клиентского тестирования.
- **Раскрытие описания новости.** Требует синхронизации не с самой операцией, а с цепочкой Room Flow → коллектор фрагмента → перерисовка списка. Диагностика показала: запись в базу завершается за 3 мс, тест падает секундой позже — то есть проблема в отрисовке, а не в операции. Закрыть это можно только вмешательством в код фрагмента, что выходит за рамки задачи тестирования. Проверяется вручную.
- **Поведение при отсутствии сети.** Автоматизация не выполняется, проверка входит в ручной чек-лист.

## 6. Тестовое окружение

- **Эмулятор:** Android Studio AVD, Medium Phone, API 29 (Android 10).
- **Язык системы:** русский. Все ожидаемые тексты берутся из `res/values-ru/strings.xml`. Локаль зафиксирована как часть окружения: при её смене изменятся результаты всех текстовых проверок.
- **Учётная запись:** `login2` / `password2`, права администратора подтверждены. Учётные записи `login1` и `login3` также имеют права администратора; записи без прав администратора не существует.
- **Бэкенд:** общий учебный стенд, используется как есть. Отсутствие сети воспроизводится авиарежимом на эмуляторе, инструменты подмены HTTP не применяются.
- **Версии сборки:** AGP 7.4.2, Gradle 7.5.1, Kotlin 1.7.10, Hilt 2.43.2, версии ktx-библиотек выровнены с core. `compileSdk` и `targetSdk` — 32.
- **Ориентация экрана:** зафиксирована портретной, авто-поворот отключён — в альбомной ориентации форма создания новости не помещается по высоте, и элементы оказываются за пределами видимой области.

## 8. Риски автоматизации

1. **Нестабильность связки версий сборки.** Исходный проект не собирался в актуальной Android Studio, версии AGP, Gradle, Kotlin и Hilt поднимались вручную. Последствие: тесты могут падать из-за поломки сборки, а не дефекта приложения. Снижение риска: зафиксировать версии и не менять их без причины, перед прогоном выполнять чистую сборку.
2. **Поля логина и пароля не имеют собственных идентификаторов.** В `fragment_auth.xml` поля ввода объявлены внутри `TextInputLayout` без `android:id`. Последствие: обратиться к ним через `withId` невозможно, приходится искать по родительскому контейнеру, и такой локатор ломается при изменении вёрстки. Снижение риска: зафиксировать выбранный способ адресации в начале работы и не менять его.
3. **Дублирование идентификаторов между экранами.** Одинаковые `id` объявлены в нескольких макетах: кнопки сортировки и фильтра, список новостей, изображение карточки. Последствие: при нескольких совпадениях в дереве Espresso выбрасывает `AmbiguousViewMatcherException`, тест падает из-за неточного локатора. Снижение риска: сужать поиск принадлежностью к родительскому контейнеру или видимостью элемента.
4. **Задержка на splash-экране.** Переход выполняется через `delay(3_000)` в корутине, с которой Espresso не синхронизируется автоматически. Последствие: тест обращается к экрану раньше, чем тот появится, либо требует `Thread.sleep` и становится нестабильным. Снижение риска: реализовать `IdlingResource` и регистрировать его для тестов с холодного старта.
5. **Зависимость от общего бэкенда.** Стенд используется всеми студентами курса одновременно. Последствие: данные меняются между прогонами, тест может получить неожиданный список или затронуть чужую запись. Снижение риска: создавать новости с уникальным заголовком и удалять их в конце теста, не полагаясь на исходное состояние списка.
6. **Ограничение выдачи в 8 записей.** Список запрашивается с жёстко заданным параметром `pages = 1`, подгрузка при прокрутке отсутствует. Последствие: созданная тестом новость может не попасть в видимую часть списка, и проверка её появления даст ложное падение. Снижение риска: проверять появление новости с учётом сортировки, ставящей свежие записи в начало списка.
7. **Тесты мешают друг другу.** После входа токен остаётся в памяти приложения на весь прогон, поэтому следующие тесты стартуют уже залогиненными и падают. Решение: сбрасывать сессию до запуска приложения, закрывать сценарий после теста, проверять набор в разном порядке.
8. **Приложение не рассчитано на автотесты.** Заставка и вход работают через корутины, с которыми Espresso не синхронизируется, и нет способа сбросить состояние снаружи. Решение: добавить в приложение `IdlingResource` для заставки и для входа, плюс точку доступа к авторизации. Логика приложения не меняется.

## 10. План сдачи работ

1. **Подготовка.** Ручной прогон чек-листа по всем экранам, фиксация найденных дефектов, замер затраченного времени для сравнения с автотестами.
2. **Инфраструктура и основные сценарии.** Настройка тестового модуля, реализация `IdlingResource`, автотесты авторизации, навигации и работы с новостями (сценарии 1–6, 8, 10).
3. **Оставшиеся сценарии.** Автотест фильтра (сценарии 7).
4. **Финализация.** Полный прогон набора, выгрузка результатов и генерация отчёта Allure, оформление сравнения времени ручной и автоматизированной проверки, подготовка к защите.
